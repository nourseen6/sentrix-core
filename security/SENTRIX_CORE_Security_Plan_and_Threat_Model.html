Security Plan and Threat Model

A staged security document for the SENTRIX CORE personal-safety system: what must be protected, who can reach it, and what the project will do at each stage of development.

Alryada University
Prepared by Nourseen Tarek
October 2026 · Academic submission
Status: security documentation for a project still in development. The wearable and the full ecosystem are not deployed.

Document purpose

1. Why this document exists

SENTRIX CORE is a personal-safety system. In its intended form it watches motion, health-related signals, sound, and location, and it can raise an emergency alert. Those are sensitive functions. A mistake can expose where a person is, expose health or audio information, or send a false alert to emergency services.

This document is the project security chapter. It has two parts. The security plan says what the team will do to reduce those risks, stage by stage. The threat model says what is worth protecting, who could reach it, and what harm that would cause.

This is a written plan for the graduation project. It is not a statement that a commercial product is already secure, and it is not a statement that the wearable has been built. Controls are marked as current work, prototype work, planned hardware, or future system behavior.

1.2 Hardware direction used by this plan

The current hardware direction is the Hardware Design Specification: nRF5340, nRF9151, BMI270, MAX86176, MAX30208, IM69D130, nPM1300, a physical SOS button, Bluetooth Low Energy, LTE-M/NB-IoT, and GNSS. That specification is a pre-schematic design. It is not a built device.

An earlier hardware description in Section 13 of the research paper used a different processor, modem, and a secure element (NXP SE050). That description is kept as design history. This plan does not add a secure element, because the current bill of materials does not include one.

2. Security plan

The plan follows the work the team can actually do. It does not treat a screen drawn in the research paper as a finished security feature.

2.1 Current stage — software and AI experiments

  • Experiments use pre-existing datasets collected by other parties, including public research sets. The team did not collect GPS, audio, medical, or child data from real users for these experiments.
  • Those files stay separate from any future records of real SENTRIX users. The project report must describe them as externally collected datasets.
  • Dataset name, source, and license are recorded before a file is placed inside a demonstration package. A license that has not been read is not described as permission to redistribute the file.
  • Passwords, API keys, and private keys are not written into source code. Raw dataset copies and model binaries are kept out of the Git repository.
  • A demonstration SOS control stays inside the project. It does not call, text, or packet a real emergency service unless the team makes a separate, explicit decision to do so.
  • When the mobile application source is reviewed, any stored token is moved to the phone’s secure storage, sessions end on logout, and server connections are recorded and kept off cleartext HTTP.

The mobile application is under development. Its source was not in the project folder inspected for this document, so login, storage, and network behavior are requirements for that code, not features already verified here.

2.2 Prototype stage — development kits

  • Each kit is labeled as a laboratory prototype, not as the finished SENTRIX band.
  • Signals on the kit are bench signals, externally collected files, or replay. A live stream of a real person’s location or voice is not used.
  • Programming and serial debug ports may stay open on a kit. That fact is written in the lab notes. The same open port is not later described as a closed product.
  • The serial link to the cellular modem is disconnected at the end of a session. SIM credentials are not printed in logs.
  • Bluetooth pairing is chosen and written down before a phone is paired. Until that choice exists, a Bluetooth test is only a connectivity test.
  • A live cellular subscription is used only after an explicit decision. The lab configuration does not contain a real emergency-service address.

2.3 Planned stage — custom wearable

These items apply only if a custom board is built. They are acceptance checks, not completed work.

  • The physical SOS button is debounced in firmware and does not depend on an AI model. That matches the Hardware Design Specification.
  • Before the board is presented as product-like, the team records whether boot checks the firmware image, and whether debug pads are removed, locked, or left as an accepted engineering risk.
  • Key storage is named honestly. If no secure storage is used, the report says so. TrustZone on the nRF5340 is a chip capability. It is not in use until a firmware split is designed.
  • A failed firmware update must still leave the local SOS button able to be detected. Sending that press off the device can wait until the radio recovers.
  • Factory reset clears Bluetooth bonds and local logs and still leaves the SOS button working.

2.4 Future stage — full SENTRIX CORE ecosystem

The research paper describes guardians, a Nearby Rescue Network, evidence storage, an operator dashboard, and an administrator dashboard. Those parts are not deployed. Before they are built, the project needs an approved access rule, authenticated emergency messages, a retention period, and a deletion rule. No cloud vendor is chosen in the project documents, and this plan does not invent one.

2.6 Privacy

Two data classes stay separate.

  • Current research data. Copies of datasets collected by external sources. The team is not the collector. Source terms still have to be read before redistribution. This document does not claim that those terms have been satisfied.
  • Future SENTRIX user data. Location, audio, health-related signals, and possible data about children or other dependents, collected by a future deployment. That data does not exist in the current experiments.

The project is being developed in Egypt. A future system that processes personal data of real people would need a privacy assessment under Egypt’s Personal Data Protection Law, Law No. 151 of 2020. That assessment is not done in this document, and this document is not legal advice. GDPR and HIPAA are reference names only. The project documents do not establish that either law applies, and this plan does not claim compliance with them.

3.4 What matters at this stage

The realistic work now is T1, T2, T3, and T4. Prototype threats T5 through T9 apply when a development kit is powered. Future threats stay in the requirements so the later design does not ignore them. They are not a description of a deployed system.

The single demonstration risk with immediate real-world harm is T9: a test SOS that leaves the lab and reaches a real emergency service. Until the team decides otherwise, demonstrations stay inside the project.

6. What to say in the examination

SENTRIX CORE will handle location, health-related signals, audio, and emergency alerts, so the project includes a security plan from the design stage. The plan is staged. Current experiments use externally collected datasets and must not send a real emergency alert. Development kits are laboratory tools. The custom band, if built, uses the physical SOS button in the Hardware Design Specification and does not claim a secure element that is not on that board. Guardians, nearby helpers, and cloud services are future architecture. Their access rules are written as a recommendation and are not yet a deployed control.

Supporting working files, kept with the project, are the detailed requirement matrix, hardware checklists, test plan, and decision register under the security folder. This PDF is the submission form of the security plan and the threat model.
